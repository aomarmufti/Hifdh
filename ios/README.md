# Hifdh on iOS

The native app is a Capacitor shell around the same `public/` web app, plus two
things a browser cannot do: **local notifications scheduled on the device** and
**native haptics**. There is no bundler — `public/` is copied verbatim — so the
web and native builds never diverge.

## Why local notifications, not push

A `WKWebView` does not receive Web Push. Rather than add APNs and a second
delivery path, the native build schedules **seven weekly-repeating local
notifications**, one per weekday, at your chosen time:

- each carries the correct body for that day (a lesson day mentions the new page)
- a rest day is not scheduled at all, so it stays quiet
- they fire with no network and no server — including in Airplane mode
- they are rescheduled whenever you change the plan

The web build keeps using Web Push via the `send-reminders` Edge Function. Same
app, two delivery mechanisms, each the right one for its platform.

## What you need

| | |
|---|---|
| Apple Developer Program | **$99/year**, your Apple ID |
| A Mac | Xcode 15+ and CocoaPods (`sudo gem install cocoapods`) |
| Time | ~30 min to first build, then 1–3 days of App Review |

None of this can be done from a Linux CI box, which is why the project is
prepared but not built.

## First build

```bash
npm install
npx cap sync ios          # installs pods and copies public/
npx cap open ios          # opens App.xcworkspace in Xcode
```

In Xcode, once:

1. Select the **App** target → **Signing & Capabilities**
2. Team: your Apple Developer team. Xcode will create the provisioning profile.
3. Bundle Identifier: `com.aomarmufti.hifdh` — change it if you want a different
   one, and change `appId` in `capacitor.config.json` to match.
4. Add the **Push Notifications** capability only if you later add APNs. Local
   notifications need no capability.

Then plug in your iPhone, pick it as the run destination, and press ▶.

## Getting it onto your phone without App Review

**TestFlight** needs no review for internal testers and is the fastest route to
a real app on your own device:

```bash
# in Xcode
Product → Archive → Distribute App → TestFlight & App Store
```

Install TestFlight on the phone, sign in with the same Apple ID, and the build
appears. This is the milestone worth reaching first.

## Submitting to the App Store

1. App Store Connect → **Apps** → **+** → New App
   - Platform iOS, Name `Hifdh`, Primary language, Bundle ID as above, SKU
     anything (e.g. `hifdh-001`)
2. Fill in: description, keywords, support URL, privacy policy URL
   (**required** — even a single page will do)
3. **App Privacy**: declare what is collected. Hifdh collects an **email
   address** (for sign-in) and **app usage data** (your revision log), both
   linked to identity, neither used for tracking.
4. Upload a build (Xcode → Archive → Distribute), attach it to the version
5. Screenshots: 6.7" iPhone is mandatory. `npm run test:e2e` writes usable
   ones to `test/shot-*.png`, though App Store Connect wants exact pixel sizes.
6. Submit for review.

## The review risk, honestly

**Guideline 4.2 — Minimum Functionality.** Apple rejects apps that are a
repackaged website. This app is at some risk because the UI is a WebView.

Arguing in its favour: it schedules real local notifications, works fully
offline, uses native haptics, and is a genuine tool rather than marketing
content. Against: the interface is HTML.

If it is rejected under 4.2, the ranked options are:

1. Add a **Home Screen widget** showing today's portion — native SwiftUI, the
   single strongest 4.2 rebuttal
2. Add **Siri Shortcuts** ("Hey Siri, what's my revision today?")
3. Rebuild the UI natively in SwiftUI, keeping `lib/engine.js` logic ported —
   the engine is pure and portable, which is why it was written that way

Do not argue with the reviewer before trying 1.

## Keeping web and native in step

`public/` is the single source. After any change to the web app:

```bash
npx cap copy ios
```

Committed: the Xcode project, `AppDelegate.swift`, assets, `Podfile`.
Not committed: `Pods/`, `DerivedData/`, and `ios/App/App/public/` — that last
one is generated by `cap copy` and would otherwise be a duplicate of `public/`
drifting in the repository.
